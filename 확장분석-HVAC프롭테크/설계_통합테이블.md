# 통합 테이블 설계서 — 영업지원-분석 × 확장분석-HVAC프롭테크

## 시나리오

시스템에어컨(SAC) 설치자재 영업지원 업무를 HVAC 종합공조자재·프롭테크(부동산+AI) 영역으로 확장해,
두 도메인의 시너지를 데이터로 검증하기 위한 설계.

## 답하고 싶은 질문 → 어느 테이블이 답하는가

| # | 질문 | 담당 테이블 |
|---|---|---|
| 1 | 영업지원-분석과 확장분석-HVAC프롭테크 데이터의 연관·상관 통합 | 테이블1 `fact_region_month_integrated` |
| 2 | 두 데이터를 통한 새로운 KPI 발견 | 테이블1 `fact_region_month_integrated` |
| 3 | 추후 협업 가능한 프리랜서/파트너 리스트·타당성 분석 | 테이블2 `dim_partner_candidate` |

## 왜 2개로 나눴는가

1·2번은 "시군구 × 월" 단위로 반복 관측되는 **집계 상태(state)**이고, 3번은 "후보 파트너 1명"이 1행인
**마스터/차원(dimension) 리스트**라 근본적으로 grain이 다릅니다. 테이블2는 테이블1의 지역 지표를
"타당성 근거"로 참조만 할 뿐, 같은 표에 넣을 대상이 아닙니다.

## 테이블 1 — `fact_region_month_integrated`

**한 행은 무엇 1개인가**: 시군구(sigunguCd) 1개가 특정 연월(year_month) 1개에 대해 갖는 통합 상태 스냅샷 1건
**테이블 성격**: 상태(state) — 사건 로그가 아니라 그 달까지 집계된 요약치를 매월 갱신하는 테이블

### 컬럼 정의

| 컬럼명 | 타입 | 의미 | 값 범위 | 결측 허용 | 비고 |
|---|---|---|---|---|---|
| region_key | STRING | 시군구코드(5자리) | 예: `41135` | N | PK 구성요소 1 |
| sido_short | STRING | 시도 단축명 | 서울/경기 등 17종 | N | |
| sigungu_name | STRING | 시군구명 | 예: `분당구` | N | |
| year_month | STRING | 연월 | `YYYYMM`, 뒤 2자리 01~12 | N | PK 구성요소 2 |
| ym_date | DATE | year_month의 표준 날짜형(매월 1일) | | N | 기존 프로젝트의 `_date` 파생 컬럼 관례와 동일 |
| n_transactions | INTEGER | 해당 시군구·월 아파트 실거래 신고 건수 | ≥0 | N(0 허용) | `data_transaction_price_seoul_gyeonggi.csv` 집계 |
| avg_transaction_price_10k | FLOAT | 평균 거래금액(만원) | >0 | Y | `n_transactions=0`이면 반드시 NULL |
| n_new_building_permits | INTEGER | 해당 월 건축인허가 건수(`archPmsDay` 기준) | ≥0 | Y | `data_building_license_seoul_gyeonggi.csv` — **대표 동 1개 샘플 기준이라 시군구 전체값이 아님(과소추정 주의)** |
| sac_eligible_grfa_sqm | FLOAT | SAC 유효수요 신축 연면적 합계(㎡) | ≥0 | Y | `영업지원-서비스분석.csv`에서 `is_sac=True & data_ym=year_month & sigungu=sigungu_name` SUM(grfa) |
| total_new_grfa_sqm | FLOAT | 전체 신축 연면적 합계(㎡) | ≥0 | Y | 위와 동일 출처, `is_sac` 무관 합계 |
| elec_commercial_sido_approx | FLOAT | 소속 시도의 상업용 전기사용량(참고용) | ≥0 | Y | `data_sac_sido_correlation.csv` — **시도 단위 값을 시군구에 그대로 broadcast한 근사치, 시군구 고유값 아님** |
| client_service_score_avg | FLOAT | 이 지역 소재 거래선의 해당 월 평균 만족도점수 | **1~5** (원래 계획한 0~100 아님 — 2026-08-22 변경, 아래 한계 참고) | 거래선이 없는 지역·달은 NULL | BigQuery `dim_client`(시군구코드)로 `fact_happycall.거래선코드`를 지역에 매핑해 월별 AVG(만족도점수) |
| misorder_rate_regional | FLOAT | 이 지역 오주문율 | 0~100% | 거래선이 없는 지역·달은 NULL | BigQuery `dim_client`로 `fact_misorder`/`fact_sales_order_line`을 지역에 매핑, [[hvac2025h2_오주문율]]과 같은 정의(분자=fact_misorder COUNT, 분모=COUNT DISTINCT 주문번호)를 지역 단위로 재계산 |

### 연결 키

- `region_key` ↔ `data_region_codes.csv.시군구코드`, `data_transaction_price_seoul_gyeonggi.csv.법정동시군구코드`, `data_building_license/ledger_seoul_gyeonggi.csv.sigunguCd`
- `(sido_short, sigungu_name)` 텍스트쌍 ↔ `영업지원-분석/영업지원-서비스분석.csv.(sido, sigungu)` — 이 파일엔 시군구코드가 없어 이름으로 조인하며, `data_region_codes.csv`를 코드↔이름 브릿지로 사용
- `year_month` ↔ `영업지원-서비스분석.csv.data_ym`, 건축인허가 `archPmsDay`의 앞 6자리
- `client_service_score_avg`/`misorder_rate_regional`: **2026-08-22 해소됨.** 이 설계를 쓸 당시엔 "매핑 테이블이 없다"고 판단했으나, 실제로는 BigQuery `crested-vortex-390400.hvac_ops.dim_client`에 거래선별 `시도`·`시군구`·`시군구코드`가 이미 채워져 있었다(당시 확인 누락). `dim_client.거래선코드`로 `fact_misorder`·`fact_sales_order_line`·`fact_happycall`을 조인해 `시군구코드`(=`region_key`)를 얻는다. 다만 15개 거래선이 커버하는 지역은 15곳뿐이라, 나머지 61개 지역은 여전히 NULL로 남는다(거래선이 실제로 없는 지역이므로 정상).

### 정합성 규칙

1. `(region_key, year_month)` 조합은 유일해야 한다(복합 PK) — 중복되면 집계가 이중 계산됨
2. `n_transactions = 0`이면 `avg_transaction_price_10k`는 반드시 NULL이어야 한다(0건인데 평균가가 존재하면 오류)
3. `sac_eligible_grfa_sqm ≤ total_new_grfa_sqm`가 모든 행에서 성립해야 한다(SAC는 전체 신축의 부분집합)
4. `elec_commercial_sido_approx`는 같은 `sido_short`·`year_month`를 가진 모든 행에서 동일한 값이어야 한다(시도 단위 broadcast 특성 검증)
5. `region_key`는 `data_region_codes.csv`에 실존해야 한다(참조무결성 — 없는 코드가 나오면 상류 오류)
6. `year_month`는 `YYYYMM` 6자리 숫자 문자열이어야 하고 월 부분은 01~12 범위여야 한다
7. (2026-08-22 수정) `client_service_score_avg`/`misorder_rate_regional`은 **거래선이 있는 지역(15곳)·그 거래선의 데이터가 있는 달(2025-07~2026-06)에서만** 값이 있어야 하고, 그 밖의 지역·달은 NULL이어야 한다. 값이 있다면 `misorder_rate_regional`은 0~100(%) 범위, `client_service_score_avg`는 1~5점 범위여야 한다(원래 계획했던 0~100점이 아님 — 원천을 `market_거래선_서비스점수`가 아니라 `fact_happycall.만족도점수`로 바꿨기 때문. "이 지표로 답할 수 없는 것" 참고)

### 심을 패턴 (5주차 검증용)

**가설**: SAC 유효수요 신축 연면적(`sac_eligible_grfa_sqm`)이 전월 대비 급증한 지역은, 2~3개월 시차를 두고
그 지역의 아파트 실거래 건수(`n_transactions`)도 증가한다 (신축 공급 증가 → 입주·거래 활성화로 이어지는
선행지표 가설). 5주차에 지역별 시차상관(lag correlation, lag=1~3개월)으로 검증.

## 테이블 2 — `dim_partner_candidate`

**한 행은 무엇 1개인가**: 향후 협업 가능한 프리랜서/외주업체 후보 1명(1개 업체)
**테이블 성격**: 상태(마스터/차원 테이블) — 후보 목록의 현재 상태(접촉 여부·타당성 점수)를 나타냄

### 컬럼 정의

| 컬럼명 | 타입 | 의미 | 값 범위 | 결측 허용 | 비고 |
|---|---|---|---|---|---|
| partner_id | STRING | 후보 고유 ID | UUID 또는 순번 | N | PK |
| partner_name | STRING | 이름/상호 | | N | |
| partner_type | STRING | 개인/법인 구분 | `개인`, `법인` | N | |
| expertise_area | STRING | 전문분야 | `HVAC설치`,`BIM설계`,`프롭테크 데이터분석`,`부동산중개` 등 카테고리 | N | |
| coverage_region_key | STRING | 주 활동 지역 | 테이블1 `region_key` 참조 | Y | 전국구/온라인 전문가는 NULL 허용 |
| years_experience | INTEGER | 경력 연차 | 0~50 | Y | |
| feasibility_score | FLOAT | 협업 타당성 점수 | 0~100 | Y | 산출 근거는 `evidence_region_key` |
| evidence_region_key | STRING | 타당성 판단의 근거 지역 | 테이블1 `region_key` 참조 | Y | 예: 해당 지역 신축 성장세가 근거 |
| status | STRING | 진행 상태 | `후보`,`접촉중`,`계약`,`보류` | N | 기본값 `후보` |
| source_note | STRING | 후보로 오른 근거/출처 메모 | 자유 텍스트 | Y | |

### 연결 키

`coverage_region_key`, `evidence_region_key` → 테이블1(`fact_region_month_integrated`).`region_key`
(같은 시군구코드 체계를 공유)

### 정합성 규칙

1. `partner_id`는 유일해야 한다
2. `coverage_region_key`가 NULL이 아니면 `data_region_codes.csv`에 실존하는 시군구코드여야 한다
3. `feasibility_score`가 존재하면 `evidence_region_key`도 반드시 존재해야 한다(근거 없는 점수 금지)
4. `status`는 정의된 4개 값 중 하나여야 한다
5. `expertise_area = "HVAC설치"`인 행은 `coverage_region_key`가 NULL이면 안 된다(설치 인력은 지역 기반 서비스)

### 심을 패턴 (5주차 검증용)

**가설**: `feasibility_score` 상위 20% 파트너 후보들의 `evidence_region_key`는, 테이블1에서
`sac_eligible_grfa_sqm` 증가율 상위 20% 지역과 70% 이상 겹친다 (타당성 점수 산정 로직이 실제
성장 지역과 정합적인지 교차검증).

## client_service_score_avg·misorder_rate_regional의 한계 (2026-08-22)

`client_name`(거래선) → `region_key`(지역) 매핑은 `dim_client`에 이미 있었음을 확인해 두 컬럼을
실제로 채웠다(`build_fact_region_month.py` 참고). 다만 이 값들을 그대로 상관분석에 쓰기 전에
아래 한계를 반드시 함께 본다:

- **표본이 매우 작다.** 거래선 15곳이 15개 지역에 1개씩 흩어져 있어, 지역당 표본이 "거래선 1개"다.
  즉 `misorder_rate_regional`은 사실 "그 지역 소재 거래선 1곳의 오주문율"이지 그 지역 전체 시장의
  오주문율이 아니다. `client_service_score_avg`도 마찬가지로 거래선 1곳의 해피콜 평균이다.
- **나머지 61개 지역(76개 중 15개만 커버)은 항상 NULL이다.** 거래선이 없는 지역이라 당연한
  결과지만, 상관분석 시 이 결측을 0이나 평균으로 채우면 안 된다 — 표본이 없다는 사실 자체가 정보다.
- **`client_service_score_avg`는 원래 설계(0~100점, `market_거래선_서비스점수`)가 아니라
  `fact_happycall.만족도점수`(1~5점)로 채웠다.** 월별 실측이 가능하다는 장점과 맞바꾼 것이며,
  두 지표는 산출 방식이 달라 서로 대체 가능한 값이 아니다.
- **거래선의 위치가 그 거래선의 "영업 활동 지역"과 같은지는 확인되지 않았다.** `dim_client`의
  시군구코드가 거래선의 사업장 소재지인지, 실제 설치/서비스가 이뤄지는 지역인지는 원본 데이터
  정의서에 명시돼 있지 않다 — 사업장이 있는 지역과 실제 서비스 지역이 다르면 상관분석의 지역
  귀속 자체가 흔들린다.
